# PostgreSQL 18.6 reset and full reindex

This is a prepared source change and an operator runbook. It authorizes no live reset, apply, redeploy, volume deletion or credential change. The user selected a deliberate reset/full rebuild of the main Envio database rather than an in-place PG16→PG18 migration. The exact destructive target and release steps still require separate review and approval. No startup or deployment hook performs a reset.

Native `safe` severity does not authorize a database-major transition. There is no CI bypass or automatic reset: perform the separately approved fresh-data release and direct native apply below. Once live main already matches the reviewed image, unrelated normal automation can resume.

## Separately approved production release

1. Record the exact project/environment, main `Postgres` service, attached volume ID/mount, effective `PGDATA`, old PG16 image and proposed immutable PG18.6 image. Record the separate cache service/volume as explicitly outside the target. Review the native plan and all destructive changes; do not infer approval from this document or a passing source check.
2. Secure a consistent main database backup/snapshot and Hasura metadata export. Account for manual data, roles/extensions and runtime-only metadata above. Verify a recovery choice: restore the old compatible database with its old image/configuration, or repeat the full rebuild. Image rollback alone cannot restore destroyed data or make PG18 data readable by PG16.
3. Pause indexer autodeploys, publisher and monitor jobs. Stop every ingestion writer, including old rolling deployments. Pause/stop Hasura writers for the database-major transition and retain its service/configuration. Stop the main `Postgres` service before the volume operation and keep it stopped until step 5 starts the approved PG18.6 image; prevent the old PG16 deployment from restarting against the reset volume. Keep frontend, gateway, bucket and eRPC cache intact. The old public snapshot may be stale during the rebuild.
4. Obtain separate approval for the recorded destructive action on the selected main volume: reset its contents, or replace it only if that exact replacement/binding has been reviewed. Retain the declared resource identity and record any provider-side old/new volume mapping. Never target the cache, bucket, unrelated volumes or shared Docker state. This repository supplies no automatic volume wipe or major-version migration command.
5. After the approved volume operation, generate and review a fresh native plan: the environment etag has changed, so the earlier artifact is stale. Before renewed approval, verify that this plan cannot deploy or restart an ingestion writer: it must exclude writer service creation/update/deployment effects, including indexer, publisher and monitor changes. Pausing autodeploy alone does not block a deployment triggered by apply. If the plan cannot isolate the main database change from writer deployments, stop; do not apply it during this stage. Obtain renewed approval for that exact plan, then apply using the authoritative [native JSON-result procedure](railway-self-hosting.md#5-apply-the-reviewed-plan). Before starting the indexer, complete only its native JSON-result checks, fresh read-only plan, complete HTTP/TCP inventory and the database checks below. Keep all writers paused until verification passes. Defer the linked procedure's live indexer routes, health, readiness and progress checks until after step 6 starts the indexer. Verify the approved Railway PG18.6 image uses the approved fresh/reset main data location, server version, effective data directory inside the mounted volume, TLS, roles and required extensions. Do not mount old PG16 cluster files as PG18 data. Restart/reconfigure Hasura only after database readiness and restore required metadata/custom configuration deliberately.
6. Deploy the unchanged Envio 3.14.1 runtime with its normal start command. Its fail-closed compatibility guard stays enabled. Empty storage may initialize normally; a confirmed incompatible schema remains paused. If the reviewed procedure needs an Envio schema reset, use the existing explicit [operator reset control](indexer-operations.md#reset-the-railway-indexer-from-your-local-machine) only after PG18 is ready and all old writers have stopped. That command is not a PG major-version converter. Never add `start -r` to ordinary startup or predeploy. Once the indexer starts, check its documentation routes remain absent and health succeeds, then monitor readiness and progress during step 7. Keep publisher and monitor jobs paused until step 8.
7. Perform a full chain reindex. Verify advancing committed heights, canonical observations, configured-chain coverage and eventual readiness. Readiness may return 503 during normal reindexing; it is not a reason to resume publication before catch-up. Fresh schema creation recreates SQL indexes; this is an application replay, not an automatic SQL `REINDEX` operation. Any separate extension/index/backup-chain follow-up requires its own review.
8. Give the publisher a fresh `INDEXER_DEPLOYMENT_ID` before the first new publication. Resume it only after catch-up/readiness and verify manifest-last publication and all referenced artifacts. Then resume monitor jobs/autodeploys. Retain recovery backups and the old bucket artifacts until acceptance.

If initialization/reindex fails or completion is uncertain, keep writers/publication paused and inspect sanitized evidence. Do not retry a destructive reset blindly, weaken the native guard or clear the eRPC database to repair the main database.

## Ephemeral local transition

Local PostgreSQL data is explicitly disposable. Compose uses fresh versioned volumes `postgres18-data` and `rpc-cache-postgres18-data`, mounted at `/var/lib/postgresql`; it does not reuse old PG17 volume contents. Integration/benchmark fixtures use the same pinned official PG18.6 family with disposable UUID-owned volumes/tmpfs and the `/18/docker` data path. No migration is required for these fresh local fixtures.

No local volume is deleted by this source change. Any later cleanup must identify only this project's obsolete PostgreSQL volumes after its containers stop; never use a shared/global prune or remove `minio-data` as a side effect. Ordinary same-major Envio schema reset instructions are separate from this fresh-volume major-version transition.

## Evidence boundary

Source tests cover exact pins, desired SDK resources/mount preservation, versioned local paths and mocked integration routing. Gateway route tests cover the static root catalogue and retained OpenAPI/data routes. They do not prove fresh PG18 image compatibility, live storage bindings, production reset safety or successful reindex. The exclusive image/integration slot must verify the actual PG18 fixtures, native persistence/rollback/reset and gateway image behavior before a release is proposed; live destruction remains separately approved.
